## T3 — R4: `Year · Ideal mileage · Upper mileage limit`

The largest of the UI tasks, because two of the three values don't exist yet.

### T3a — buy-point sweep in `packages/core`

There is no buy-point search today: `buyOdo` is simply `inputs.buyOdo ?? vehicle.pinned_buy_odo`
(`engine.ts:35`). This is cost math, so it belongs in `packages/core`, not the web app.

New export in a new `packages/core/src/buypoint.ts`:

```
buyPointSweep(vehicle, constants, inputs, { draws, step }) -> {
  idealOdo: number;      // argmin P50 over the feasible grid
  idealP50: number;
  idealYear: number;     // deriveBuyYear(vehicle, idealOdo, am, now_year)
  upperOdo: number | null;
  grid: { odo: number; p50: number }[];
}
```

- Grid = 10,000-mile steps across `feasibleOdoRange(vehicle, annualMiles, constants.now_year)`
  (already exported from `feasibility.ts` — **reuse it, don't re-derive**), clamped at ≥ 0 and
  capped at the vehicle's `eol_maintained_miles`.
- Each point calls `costPerMile` with `{...inputs, buyOdo, draws: SWEEP_DRAWS}` and a fixed seed, so
  the sweep is deterministic and comparable point-to-point.
- `upperOdo` = walk *upward* from `idealOdo` and take the last odometer whose
  `p50 <= idealP50 * (1 + tolerance)`, **stopping at the first violation**. Contiguity matters — a
  non-contiguous rule could return a far outlier that happens to dip back under tolerance.
- Degenerate cases: a feasible range narrower than one step, or a single grid point, returns
  `idealOdo` = that point and `upperOdo: null`. The UI must handle `null`.

New `calibration.ts` entries, each with a doc comment marking it JUDGMENT:
- `sweepDraws: 300` — reduced-precision sweep (the survey drawer's 400-draw reduction is the
  existing precedent).
- `sweepStepMiles: 10_000`.
- `worthwhileP50Tolerance: 0.05` — "still worth buying" = within 5% of the cheapest feasible point.

Unit tests in `packages/core/test/`: a monotone-cost fixture returns its true argmin; the tolerance
walk stops at the first violation and does not jump a gap; a single-point feasible range returns
`upperOdo: null`.

**This does not change any existing reference output** — `costPerMile` itself is untouched, so
`npm test -w @opencawr/core` must stay green **without** regeneration. If it doesn't, the change
leaked; fix the leak, don't regenerate.

## T5 — R7: PHEV energy model revision

**Files:** `packages/core/src/engine.ts` (`energyPerMile`), `src/types.ts`, `opencawr_data.json`,
`ASSUMPTIONS.md`.

Current formula:
`uf × (kwh_per_100mi/100) × elec × dcfc_phev + (1 − uf) × (gas / phev_gas_mpg)`.

**1. Mileage-dependent utility factor (anchored).** Add `electric_range_mi` to `VehicleSpecs`
(optional) and populate the four PHEVs from EPA: Volt 53, RAV4 Prime 42, Prius Prime 25, Pacifica
PHEV 32 — verify each against EPA and cite the model years used, since Volt (Gen 1 is 38 mi) and
Prius Prime (2023+ is 44 mi) differ by generation. Which generation each seed row represents must be
stated, not assumed.

Fleet utility factor is by definition the share of miles falling within electric range,
`E[min(d, R)] / E[d]` over the daily-driving-distance distribution `d`. Model `d` as exponential
with mean `d̄ = annualMiles / 365` — the gamma-shape-1 case, which gives a closed form with no
special functions:

```
ufRaw(R, annualMiles) = 1 − exp(−R / (annualMiles / 365))
```

Anchor so each car keeps its seed UF at the baseline `constants.annual_miles` (13,000):

```
uf = clamp(uf_seed × ufRaw(R_eff, annualMiles) / ufRaw(R, constants.annual_miles), 0, 1)
```

This is a **J2841-shaped approximation, not J2841 itself** — say exactly that in the ledger, and do
not cite J2841 as a source for the numbers. The anchor means the curve supplies only the
*sensitivity* to annual mileage; each car's absolute calibration at baseline is unchanged. Sanity
check at 13k mi/yr: raw values are Volt 0.774 (seed 0.80), RAV4 Prime 0.693 (0.75), Prius Prime
0.505 (0.55), Pacifica 0.593 (0.45) — three of four land within ~9%, which is the evidence the shape
is reasonable; Pacifica is the outlier and the anchor absorbs it.

**2. PHEV pack degradation.** Reuse the existing `constants.ev_kwh_degradation_mult` (1.08) — do not
add a constant. Apply it *both* ways: `kwh_per_100mi × 1.08` and `R_eff = R / 1.08`, so degradation
raises electric consumption **and** shrinks range, which lowers UF and shifts miles to gas. Document
that this is a fixed mid-life multiplier (the same treatment EVs already get), not a function of the
holding period.

**3. DCFC premium.** `constants.dcfc_elec_mult_phev` 1.06 → **1.00**. PHEVs charge at home overnight
and several cannot DC fast charge at all. Leave the constant in place at 1.00 rather than deleting
it, so the decision stays visible in the data.

**4. EPA convention.** Verify all four `kwh_per_100mi` values (31 / 25 / 36 / 40) are EPA
**electric-mode** consumption, not the blended figure — a blended row would double-count that
vehicle's gas portion. Record the convention explicitly in §B so a future pipeline-assembled PHEV
can't reintroduce the bug.

**Signature change:** `energyPerMile(vehicle, constants, gas, elec, annualMiles)`. Update the single
call site in `costPerMile` (`engine.ts:68`) and the re-export in `index.ts`. The EV, gas and hybrid
branches are untouched.

**Then:** `npm run gen-reference -w @opencawr/core`, stating in the commit body that this is a
deliberate model revision with regenerated reference outputs.

**Verify:** core tests green post-regeneration; diff the regenerated outputs and confirm **only the
four PHEVs moved** — any gas/EV/hybrid movement means the refactor leaked. Then confirm by hand in
`vite preview` that changing annual miles now moves a PHEV's energy cost, which is the entire point
of item 1.

**Ledger:** §B rows for the anchored UF, the PHEV degradation treatment, the DCFC change, and the
EPA electric-mode convention; plus an explicit §B/§E note that **energy sits outside the Monte
Carlo**, so fuel-price and efficiency risk contribute zero variance to P50/P75/P90 — an accepted,
documented v2b limitation, deferred by owner decision this session.
